# Security audit — 2026-05-02

Sprint E3 walked the four hardening gaps the broader app audit
flagged. Three of the four turned out to be already addressed in
the existing codebase; the fourth is partially verified and the
rest of it needs a dedicated multi-day pass.

## E3 #11 — Startup error message redaction

**Hypothesis:** `.expect("…")` / `.unwrap()` calls during config init
might leak secret-flag names in panic messages.

**Walk-through:**
- `services_rs/bff_gateway/src/main.rs` — every `.expect("…")` / `.unwrap()`
  match falls inside `#[cfg(test)] mod` blocks (router_fallback_tests
  starting at line 1683 etc.).
- `services_rs/bff_gateway/src/config.rs` and `state.rs` — same: all
  hits live inside test modules (`ENV_LOCK.lock().unwrap()` for
  serialised env mutation, `expect("signer")` in test helpers).
- `services_rs/bff_gateway/src/bin/schema_migrate.rs` — uses
  `unwrap_or_default()` for `DB_URL`, then `eprintln!` + `exit(2)`
  with a generic message that does not name the secret. Failure
  paths use `tracing::error!(error = %e, "…")` with descriptive but
  non-leaking labels.

**Verdict:** ✅ No fix needed. Production startup paths already
emit generic, non-secret-naming messages.

## E3 #10 — Structured logging PII audit

**Hypothesis:** `tracing::*` macros might pass raw token / phone /
email values as span fields.

**Walk-through:**
- All sensitive identifiers in `auth.rs` go through helpers before
  emission: `hash_prefix(&account_id)`, `token_hash_prefix(&token_hash)`,
  `path_hash` for path fingerprints. See e.g. `auth.rs:2412, 2898,
  3096-3136, 6962`.
- `BFF_TOMTOM_API_KEY not configured` and similar warnings emit
  the env-variable *name*, never the value.
- `password signup … failed` messages contain the literal string
  "password" but only an opaque `error = %e` (sqlx error type),
  not the credential.
- Regex `tracing::.*\!\(.*\b(phone|email|token)\s*=\s*[^h%]` — no
  matches anywhere in `services_rs/` or `crates_rs/`.

**Verdict:** ✅ No fix needed. Logging is exemplary; the
hash-before-emit pattern is consistent.

## E3 #9 — Signal-style chat nonce initialisation

**Hypothesis:** the chat ratchet might reuse a nonce on the same
key, which would be catastrophic for an XSalsa20-Poly1305 box.

**Walk-through:**
- `clients/shamell_flutter/lib/core/chat/ratchet_models.dart` does
  not handle nonces directly.
- The actual nonce generation lives in
  `clients/shamell_flutter/lib/core/chat/chat_service.dart:541-544`:

```dart
final rnd = Random.secure();
final nonce = Uint8List.fromList(
  List<int>.generate(24, (_) => rnd.nextInt(256)),
);
```

  - 24 random bytes from Dart's CSPRNG (`Random.secure()`).
  - Generated fresh per outbound message.
  - Birthday bound at 2^96 messages on the same key → not reachable
    in any realistic mobile-chat lifetime.

**Verdict:** ✅ No fix needed. This is a sealed-sender single-shot
box construction, not a stateful ratchet, so per-message random
nonces are the correct pattern.

## E3 #6 — Cross-tenant IDOR surface

**Hypothesis:** `owner_team` / `team_id` resource lookups might
not be properly scoped to the requesting principal.

**Walk-through (spot check):**
- `coach_load_admin_risk_action_map` does `SELECT … FROM
  auth_coach_admin_risk_actions` with no `WHERE`. Initially looks
  alarming.
- All call sites (`handlers.rs:27238, 27385, 28907`) sit behind
  endpoints whose first action is `auth::require_ride_admin_principal
  (&state, &headers).await?` — these are intentional ride-admin /
  ops dashboards that read the full state.
- Handler-level authz coverage:
  - 54 `require_session` calls in `handlers.rs`.
  - 12 `require_ride_admin` calls in `handlers.rs`.
  - 270 total `pub async fn` exported handlers.
- The remaining ~200 handlers route through the workspace-level
  authz layer in `crates_rs/shamell_common/src/internal_auth.rs`
  + `services_rs/bff_gateway/src/authz.rs::require_admin`.

**Verdict:** 🟡 **Spot-check passed; full audit remains an open
multi-day task.** The handlers we inspected are correctly gated.
A complete cross-tenant IDOR sweep across all 270 handlers requires:

1. A canonical list of "team-scoped" resources (auth_coach_admin_risk_
   actions, auth_coach_admin_review, auth_workforce_…), enumerated
   from the schema.
2. For each resource, every handler that reads/writes it must be
   verified to either:
   a. Filter by the caller's `team_id` / `owner_account_id`, OR
   b. Be gated by `require_ride_admin` / `require_workforce_admin`.
3. An automated test harness that posts an authenticated request
   from team A against a team-B-owned resource and asserts a 403.

This is queued as a follow-up sprint; tracking under
`services_rs/bff_gateway/REFACTORING.md` once the handler
decomposition lands and the resource list is easier to enumerate.
